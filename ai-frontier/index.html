Agent 规模化后的工具与成本问题：Gemini API 推出 Tool Retrieval，按需加载工具 schema 以压缩输入 token

编辑判断：

Google 在 Gemini API 预览 Tool Retrieval，让模型只看到工具名与描述、按需加载参数 schema，直指工具库膨胀带来的输入 token、延迟与选择准确率问题。

为什么现在看：

2026 年 11 月 19 日，Google 在 Gemini API 的 Interactions API 中预览 Tool Retrieval；同一周，微软研究院等机构发布 TokenEconomizer，用历史会话削减编码 Agent 成本。两件事都把「工具与上下文按需加载」摆到 Agent 规模化的成本议题中心。

展开深读 · 机制、分歧与证据
材料陈述

发生了什么

2026年11月19日，Google 在 Gemini API 的 Interactions API 中推出 Tool Retrieval 预览功能，产品经理 Lucia Loher 与 Google DeepMind 研究科学家 Nora Kassner 联名宣布。其做法是让模型仍能看到所有被延迟加载工具的名称与描述，但参数 schema 不进入上下文，只在当前任务需要时按名称加载；开发者添加 tool_search 工具并对指定工具设置 defer_loading: true 即可启用，还支持远程 MCP 服务器和客户端侧检索。Google 称该功能用于减少输入 token、降低延迟，并在候选工具列表变长时维持工具选择准确率，同时可与前缀缓存配合。同期 Microsoft Research 的 TokenEconomizer 博文也把加载未使用工具列为 AI 编码 agent 的成本浪费来源之一，反映出工具规模膨胀正成为 agent 落地的共同议题。

Google AI ↗Microsoft Research ↗
分析判断

为什么会这样

工具库变大后，每次请求都把全部参数 schema 塞进上下文，输入 token 会随工具数量线性增长，候选列表越长，模型挑错工具的概率也越高。举例来说，一个退款 agent 连接 50 多个函数，每个函数的参数定义都要随每次请求发送；按 Google 的说法，模型此时只需知道 issue_refund 的名称和描述，等用户说“订单 A-1042 损坏，退 40 美元”时，模型先按名称搜索该工具，API 再在同一请求内加载它的 order_id、amount 等 schema，最后由模型发出函数调用。这意味着被延迟的 schema 不占据提示开头，Google 称其因此能与前缀缓存配合。需要说明，这是 Google 公布的工作流程与设计意图，上述权衡是分析，而非其披露的内部实现细节。Microsoft Research 的 TokenEconomizer 博文也把加载未使用工具列为成本浪费来源，但其针对编码 agent，机制与 Gemini 的按需加载不同。

Google AI ↗Microsoft Research ↗
分析判断

放在一起怎么看

把两份材料放在一起看，它们从不同层面回应同一个问题，但并不构成互相验证。Google 的 Tool Retrieval 是厂商在产品接口层给出的解法：由 API 自身承担搜索与按需加载，开发者改动很小，面向的是通用 agent 的工具库膨胀；其减少输入 token、降低延迟、维持选择准确率的主张属于 Google 的说法，尚无第三方复现。Microsoft Research 的 TokenEconomizer 则是研究侧的编码 agent 插件，用工具裁剪、微技能与失败循环干预三项机制，在 277 个 SWE-Bench 任务上报告成本下降 18.4–30.9%。编辑推断：前者把工具加载权交给模型运行时，后者把取舍权交给跨会话经验，二者路径互补而非竞争，但两者都只是各自来源的结论，不能合并成“按需加载已被产业验证”。对用户而言，短期可用的是 Gemini 预览功能，其实际节省幅度取决于工具库规模与调用分布，材料未给出具体 token 或延迟数值，这部分仍是未知。

证据边界

还有什么不能下结论

目前仍有多项内容不能下结论。Google 披露的减少输入 token、降低延迟、维持工具选择准确率，均属厂商自报，材料没有给出具体 token 降幅、延迟数值或对比基准，也没有第三方独立复现；文中出现的 Gemini 3.6 及以后模型、gemini-4-hydrogen 示例模型属于材料原文表述，其实际可用范围与版本对应关系未知。价格方面材料只说按标准费率计费、启用 tool_search 会增加一小块固定输入 token，因此净成本是否下降取决于工具库规模与调用分布，不能推成普遍省钱。TokenEconomizer 的 18.4–30.9% 来自 277 个 SWE-Bench 任务和五个 agent–模型组合，作者也承认早期任务可能更贵，不能直接外推到 Gemini 场景。两者来源不同、机制不同，不应互相验证。

分析判断

为什么会这样

这种同步源于同一套底层机制的错配：桌面 Agent 要跨进程代替用户点击、读界面、改文件，往往只能借道原本为无障碍设计的辅助功能与完全磁盘访问等宽泛授权，单个工具实际所需远小于获批范围。少数派举例，一套只操作 Keynote 的自动化流程，过去也要拿到可读取所有应用的全局权限；Apple 因此在 macOS 27.3 Beta 2 中把控制类权限拆成面向辅助工具的辅助功能与面向自动化工具和 AI Agent 的 System & App Protection Override，后者可按目标程序限定并设置每次询问或随时允许。这是分析：能力越强，越依赖宽授权，平台只能把授权收窄到具体对象。

材料陈述

发生了什么

2026年11月16日，微软研究院与微软安全部门联合 UC Berkeley 发布开源插件 TokenEconomizer，用于在不修改编码 Agent 及其底层模型的前提下，从同一代码仓库的历史会话中学习，以减少后续会话的 token 浪费。微软研究院称，在 277 个来自 SWE-Bench、覆盖六个仓库的真实修 bug 任务上，跨五种 Agent 与模型组合平均降本 18.4%–30.9%，且 Pass@1 在四组中上升。同日，Hugging Face 宣布把 Inference Providers 的语言模型请求从自研路由器切换到 OpenRouter，按其对各提供商的实时价格、速度和可靠性测量择优，并在失败时自动重试；Hugging Face 称图像、视频与音频生成仍走自有通道，定价不变、不加价。

分析判断

为什么会这样

这种转向的机制在于：Agent 运行时的成本有很大一部分并非来自“想得不够聪明”，而是来自重复劳动和路由失配。TokenEconomizer 的做法已由微软研究院披露：Agent 每次会话都会把指令、工具描述和会话历史发送给模型，而在同一仓库连续做任务时，30% 的工具调用重复了此前任务中的动作，每轮下发的 23 个工具描述里有 16 个从未被调用，17% 的失败任务占用了 32% 的开销。举例来说，某个仓库里“如何跑测试”这类信息第一次由 Agent 摸索得出，若不记录，下一次会话就得再摸索一遍并再付一次 token；TokenEconomizer 把这类仓库特定经验写成一行笔记，等多次会话确认后才加入起始上下文，证据矛盾就撤下，同时裁掉历史显示用不上的工具，因此省下的是重复发现与无关上下文的开销。推理侧同理，Hugging Face 把路由交给 OpenRouter，后者按实时价格、速度和可靠性为每次请求挑提供商，某家变慢或出错就把流量移走并在同一次调用内重试，减少的是排队、故障与选错供应商带来的无效消耗。需要说明的是，这些解释基于两家公开的机制描述，属于对“运行层为何成为成本战场”的分析判断，而非对未披露内部实现的推断。
